# Transaction interpretation

Transaction details expose a versioned `interpretation` object, a **What happened** panel and **State changes**. These describe supported operations, classic swaps, supported Soroswap and Aquarius exchanges, committed token movements and metadata writes. Raw envelope, result, metadata, operation and event XDR remain available.

## Supported descriptions

- Classic payments, account creation and account merges describe the operation's intent, participants and available amounts.
- Classic strict-send and strict-receive path payments show request limits separately from reconciled execution. A successful conversion is labeled **Swap assets** only when its result claims reconcile; see the rules below.
- Top-level Soroban invocations identify the contract and function. Supported Soroswap and Aquarius router exchanges include reconciled amounts and pool routes. Other invocations remain contract calls; a function named `swap` alone does not establish an exchange.
- Committed transfer, mint, burn and clawback movements have separate actions for supported events. A classic payment/account operation and its corresponding token movement are not counted as two actions.
- Unsupported operations are explicitly labeled as having no plain-language interpretation. Their actual application status is still shown.

Classic amounts and asset identities come from the envelope. Token effects are derived from source metadata using the same event rules as the token decoder; retained derived payloads are not trusted to invent effects during an upgrade. SAC identity does not establish contract deployment. Unknown custom-token decimals remain unknown and the UI displays exact base units.

Each action includes its zero-based operation index, source (`operation` or `token_event`), related committed event indexes, stable ID, status and optional result code. For supported contract swaps, `source_account` identifies the envelope operation source, while `from`, `to` and the protocol-specific swap's `trader` identify the actual token owner and recipient. Other operation actions retain their existing source-account semantics. None of these fields proves the caller of an arbitrary internal contract invocation. Routing information is retained when supplied.

## Applied and unsuccessful actions

| Status        | Meaning                                                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `applied`     | The transaction succeeded and this operation or committed token effect was applied                                        |
| `failed`      | The transaction failed and the matching operation result explicitly reports failure                                       |
| `not_applied` | The transaction failed; this operation has no committed changes, without claiming whether it was executed before rollback |

A failed transaction never has applied actions or interpreted token effects. Successful operation codes inside a failed transaction do not establish a completed payment. Fee accounting remains separate: failed transactions can still have committed fee/refund events.

## Failure explanations and diagnostics

The `failure` object retains the outer transaction code, optional fee-bump inner code, a readable explanation and explicit per-operation failures. Explanations cover common transaction preconditions, payment/account errors, authorization failures and Soroban invocation/resource failures. Unsupported result codes receive a generic explanation with the original code preserved. Fee-bump errors use the inner result when available.

Typed SCError values in diagnostic topics and data are exposed separately. A numeric contract-defined error is displayed with its original code and no guessed meaning. Diagnostics may include handled errors from a successful transaction and never override transaction/operation result codes. At most 64 diagnostic errors are returned, with traversal limited to 32 nested containers. `diagnostics_truncated` directs users to the retained raw trace when these bounds are exceeded.

## Classic swaps and path payments

`action.path_payment` includes the mode, send/destination assets, envelope limits, requested intermediate path, and nullable execution. Strict receive fixes the output and caps the input; strict send fixes the input and floors the output. Request limits are never presented as actual execution amounts.

For successful transactions, the decoder validates the operation result type, destination, delivered asset/amount and request limits. It reads order-book claims (including legacy v0) and liquidity-pool claims from the operation result. Claims describe the maker: assets bought are the taker's input, and assets sold are the taker's output. Exact integer netting across every asset verifies the source debit, destination credit and zero net intermediate amounts. This supports multiple hops, split fills and repeated intermediate assets without adding their amounts to the source debit. Result claim indexes and venues provide provenance. Zero-amount offer-cleanup claims do not count as trades.

An unsuccessful transaction has no executed exchange even when one operation's result reports success before atomic rollback. Missing or inconsistent claims also leave execution null. A same-asset path payment without trades remains a payment. Cyclic routes with the same input/output asset are retained as path payments without a reconstructed exchange. Transaction fees are separate from swap amounts.

These rules cover the Stellar DEX, including classic liquidity pools. Soroban exchanges use a separate adapter and evidence model below. A function called `swap`, matching event name, or opposing token movements alone never establish a swap.

## Soroswap router exchanges

`action.contract_swap` identifies supported successful exchanges through the registered Testnet router `CCJUD55AG6W5HAI5LRVNKAE5WDP5XGZBUDS5WNTIVDU7O264UZZE7BRD`. Adapter version 1 supports `swap_exact_tokens_for_tokens` and `swap_tokens_for_exact_tokens`, using the ABI and events from [Soroswap core commit 6eade008](https://github.com/soroswap/core/tree/6eade008ee6794075ad941609e0fef0d1124d3eb/contracts/router) and its [Testnet deployment manifest](https://github.com/soroswap/core/blob/6eade008ee6794075ad941609e0fef0d1124d3eb/public/testnet.contracts.json).

Interpretation requires a successful transaction with one top-level router invocation, a supported typed request, exactly one matching committed router event, and an identical returned amount vector. Actual input/output amounts must satisfy the requested exact-input or exact-output limits. The adapter requires two to seventeen distinct path tokens and positive i128 executed amounts. It derives each pool from the registered factory and sorted token identities using the deployed router's [pair-address derivation](https://github.com/soroswap/core/blob/284a5e14a67cfc35b450de476336a92143bf2366/contracts/library/src/tokens.rs), then reconciles the ordered transfers from trader to first pool, between pools and back to the trader. Intermediate transfers serve as both one hop's output and the next hop's input; they are counted once.

The successful invocation result must also commit to this metadata: the decoder hashes the XDR `InvokeHostFunctionSuccessPreImage` containing the return value and all original operation contract/system events, then checks equality with the result's success hash. This follows [Stellar Core's result construction](https://github.com/stellar/stellar-core/blob/362dbc5184c5fdc0d6e898f3046639dc5e2a4f32/src/transactions/InvokeHostFunctionOpFrame.cpp#L1043). Diagnostic events and transaction-level fee events are excluded. Rewritten historical event metadata, including CAP-67 transformations, can fail this equality check; the adapter preserves the generic contract-call display rather than guessing which events to remove.

The committed router event must follow the transfer chain. Other pool events remain available as raw evidence. Additional token transfer/mint/burn/clawback effects make this adapter's exchange attribution ambiguous and leave the invocation as a contract call. Failed calls, nested router calls, unsupported routers, repeated-token routes, inconsistent requests/events/returns and mismatched transfers also receive no `contract_swap` object. Token movement actions remain visible and reference the same events; they do not represent additional transfers beyond the swap.

`verification: registered_router_and_transfers` describes these checks. It does **not** establish historical WASM identity: `router_wasm_hash` is null when this transaction's metadata does not reveal the executable. A conflicting observed executable rejects the adapter. Router registration is based on a pinned deployment manifest, not a live network registry or certification of arbitrary contracts. Matching custom-token events establishes the observed event evidence, not certification of token compliance or proof of every contract's balance semantics. The adapter does not independently reconstruct pool reserves or pricing.

The response keeps exact base-unit strings for request limits, every returned amount and every hop. `exact_input` fixes `input_limit` and floors `output_limit`; `exact_output` fixes `output_limit` and caps `input_limit`. `trader` is the actual token owner and recipient established by the request and transfer evidence, and can be a contract. `action.from` and `action.to` both identify this trader, while `action.source_account` separately retains the envelope operation source and can differ from the trader. `deadline` is the exact u64 Unix timestamp from the request. Transaction fees are excluded. The UI displays actual amounts, request limits, trader, route, event indexes, executable observation and raw evidence separately; unknown token decimals remain base units.

This adapter covers the registered Soroswap deployment and supported methods above. Other Soroswap deployments, nested calls and aggregators remain unsupported.

## Aquarius router exchanges

`action.aquarius_swap` identifies supported calls through the registered Testnet router `CBCFTQSPDBAIZ6R6PJQKSQWKNKWH2QIV3I4J72SHWBIK3ADRRAM5A6GD`. Adapter version 2 covers direct `swap` and chained `swap_chained` exact-input calls, chained `swap_chained_strict_receive` exact-output calls, and bounded single-group exact-input `swap_split` calls. The router address is published in [Aquarius developer prerequisites](https://docs.aqua.network/developers/code-examples/prerequisites-and-basics). The [current router reference](https://docs.aqua.network/developers/reference/router-and-pool-contracts) documents the five strict-receive arguments and returned actual input. The [routing guide](https://docs.aqua.network/developers/code-examples/executing-swaps-through-optimal-path) describes exact-input and strict-receive interfaces.

Interpretation requires a successful transaction with one top-level registered-router invocation, a supported typed request, matching return evidence and the successful invocation result commitment over original operation events and return value. Exact-input calls return the final output: input must equal the requested amount and output must meet the requested minimum. Strict receive returns actual net input: spending must not exceed the funded maximum, and final output must equal the requested output. Each hop reconciles one committed router event, one pool trade event and the exact ordered input/output token transfers. Pool addresses come from agreement among those events and transfers. They are **not** deterministically derived or independently checked against a pool registry. `pool_index` preserves the request's original 32-byte identifier as lowercase hex; router events do not independently verify its registry mapping, and it is not a WASM hash.

A direct swap has one pool and two token transfers: trader to pool, then pool to trader. Chained and split exact-input routes include initial trader-to-router funding, router-to-pool and pool-to-router transfers for every hop, and the final router-to-trader payout: `2 × hops + 2` transfers. All settlement indexes remain in `transfer_event_indexes`. Intermediate amounts and duplicate descriptions in token movement actions are not added to swap volume. Per-hop amounts, pool token lists, request indexes and router/trade/transfer event indexes remain inspectable.

For strict receive, the router receives the maximum input, pays the requested output, then returns any positive unused input **after the output payout**. The adapter requires this observed ordering. `input.amount` is the net amount spent, never the maximum funding debit: `funded_amount - refunded_amount`. `output.amount` is the delivered output. `input_limit` retains the maximum and `output_limit` the exact requested output. `settlement` preserves the funded/returned input amounts and funding, input-return and payout event indexes. A zero return requires no return event and `refund_event_index: null`; an extra zero-valued transfer is not accepted as a refund. Exact-input routed swaps have a zero returned amount. Input-token returns are separate from transaction fee refunds. Historical source variants with a different return ordering remain unsupported.

Split interpretation is limited to **one outer group with two through eight branches**, all sharing input/output token identities. Positive `weight_bps` values must sum to 10000, and every `total_input × weight_bps` allocation must divide exactly by 10000. Fractional allocations are left as generic calls because the current rounding/dust policy is not independently established. Each route preserves its own token `path`, actual input/output and zero-based `hop_indexes` into the flattened top-level pool evidence. The split's root `path` is empty, since its branches do not establish one linear path. Aggregate input/output sum branch endpoints once. All branches together have at most sixteen hops and use distinct pools. Multiple outer groups, exact-output splits, reused pools and other unsupported forms remain generic contract calls. These bounds describe the adapter, not complete protocol support or a verified universal allocation policy.

The adapter bounds a linear path to seventeen distinct exchanged token contracts and all routed executions to sixteen total hops, with pool token lists containing two through eight sorted distinct contracts. These are implementation bounds, not universal protocol maxima; the official routing guide separately recommends at most four pools. Ambiguous additional token effects, repeated tokens within one path, missing/mismatched events or returns, failed calls, nested calls and unsupported methods receive no `aquarius_swap` object. Request limits remain distinct from actual execution, and token amounts with unknown decimals are displayed as exact base units.

`verification: registered_router_events_and_transfers` states the evidence checks performed. `router_wasm_hash` is only an executable observation from this transaction's metadata and is null when absent. Conflicting observations reject the interpretation, but there is no independently verified expected Aquarius code hash. An observation does not establish a match to pinned or audited deployed code. The [2025 router source snapshot](https://github.com/Certora/soroban-amm-contest-prep/blob/15eeca6a308f175481d13c9c3d2463d1686fb10e/liquidity_pool_router/src/contract.rs), [router events](https://github.com/Certora/soroban-amm-contest-prep/blob/15eeca6a308f175481d13c9c3d2463d1686fb10e/liquidity_pool_router/src/events.rs) and [pool event definitions](https://github.com/Certora/soroban-amm-contest-prep/blob/15eeca6a308f175481d13c9c3d2463d1686fb10e/liquidity_pool_events/src/lib.rs) help explain event shapes; the older snapshot's refund ordering differs from the retained current executions and is not evidence of current deployed behavior. Supported strict-receive settlement and split shapes are validated against retained source XDR. No independently verified current split allocation/rounding specification is claimed. Publication in an audit-contest repository is not proof of execution-time code identity. Custom-token event agreement does not certify token compliance or every contract's balance semantics.

`action.from`, `action.to` and `aquarius_swap.trader` identify the actual token owner/recipient; `action.source_account` separately retains the envelope operation source. Transaction fees are excluded. No deadline or pool fee is inferred: these fields are not part of this adapter response, and an ambiguous pool-event fee denomination remains raw evidence. Other Aquarius methods, unsupported split forms, nested swaps, other protocols and arbitrary applications remain outside this interpretation. Legacy adapter-version-1 responses omit `settlement` and `routes`; the UI continues to display their original exact-input evidence without inventing custody or branch data.

## Committed state changes

`interpretation.state_changes` contains one item for each committed `CREATED`, `UPDATED`, `REMOVED` or `RESTORED` metadata record, in source order. `STATE` is a baseline and does not count as a write. Records preserve their group (`transaction_before`, `operation` or `transaction_after`), nullable zero-based operation index, original change index, optional baseline index and full ledger-key XDR.

Before values are paired by the entire ledger key within the same metadata group. A baseline for another contract-data key, account or durability is never reused. Restored entries can provide the baseline for a later update/removal. A missing baseline is `unknown`, a creation starts `absent`, and a restoration starts `archived`; these cases are distinct. Removed entries end `absent`. Operation writes are omitted for failed transactions; committed transaction-level changes can remain.

Readable snapshots project account balances/sequence/flags/subentries/home domain, trustline balances/limits/flags, contract data and instance storage/executable, contract code hash/size, TTL, offers and account data. Integer quantities are strings; account amounts are stroops and trustline/offer amounts are base units. Strings containing NUL or invalid UTF-8 are represented as `{"encoding":"hex","value_hex":"…"}` so their exact bytes survive JSONB storage; nested keys/values use the same rule. Snapshots explicitly identify a partial projection, with `xdr_only` for entry kinds without readable fields. Full entry extensions, unsupported fields and WASM bytes remain in metadata XDR rather than being duplicated in every snapshot. The UI presents ten writes per page and wraps long values on narrow screens.

This is transaction metadata evidence, not a complete application narrative or current account/contract state. It excludes ledger-level evictions/upgrades and fee processing recorded outside `TransactionMeta`. Do not add these partial balance changes to infer network balances or fee totals. The [fee breakdown](standards.md) uses its own committed events and reconciliation rules.

## API and upgrades

`GET /api/v1/transactions/{hash}` includes the full interpretation. Transaction lists omit this object to keep list responses lightweight. The interpretation has its own `version`; the current version is 5. See the [OpenAPI specification](openapi.json) for exact fields and nullability.

Migration 7 introduces `interpretation_version`; migration 8 adds state changes and classic swaps; migration 9 adds the Soroswap adapter; migration 10 adds Aquarius exact input; migration 11 adds strict receive, routed settlement evidence and bounded split routes. Each enriches retained transactions atomically under the ingestion lock. The upgrade checks that payload identity, source XDR, source account, execution status and timestamp agree with their stored columns, then validates the envelope identity and source accounts. It changes only the interpretation and its version. Raw data, prior payload fields, event/movement IDs, checkpoint, dataset and counters remain unchanged. A source decoding or consistency error rolls back the entire migration, including prior update batches. Already-current rows are skipped, and replaying an unchanged ledger remains a no-op.

```bash
docker compose build
docker compose stop indexer
docker compose up -d
```

Keep the existing database volume. Migration from retained data is not a historical network backfill. Decoder, PostgreSQL, API and browser coverage is described in [testing](../tests/README.md).
